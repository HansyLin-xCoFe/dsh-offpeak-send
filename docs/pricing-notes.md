# dsh-offpeak-send · DeepSeek 峰谷（谷价）定价调研笔记

- 调研：pricing-scout（Research teammate）
- 访问日期：**2026-11-09**（Asia/Hong_Kong，UTC+8，本机系统时间）
- 用途：确定 `dsh-offpeak-send`（DSH Web 输入框「定时发送 / 等谷价」插件）预设的默认窗口与 UI 口径
- 口径：以 2026-11-09 当日**官方定价页**为准；官方明确「价格可能变动」，UI 不应把数字写成永久承诺。
- 范围：本文件只做定价事实调研；插件代码（`plugin/*`、`scripts/*`）由 Lead 负责，本文件未改动它们。

## 0. TL;DR（先看这六条）

1. **旧的 00:30–08:30（北京时间）夜间优惠已过时**：那是 2025 年 2 月的错峰方案，当前官方文档已不再这样定义。
2. 2026-08-17 起 DeepSeek 改为「峰谷定价」：**高峰 = 北京时间周一至周五 `09:00–12:00`、`14:00–18:00`（不含中国法定节假日）**；**其余全部为空闲/谷价时段**，包括全部周末与中国法定节假日。
3. **谷价 = 高峰价的 50%**（即 5 折），对当前在售的 `deepseek-flash`、`deepseek-v4-pro` 两个模型族都适用，缓存命中输入 / 缓存未命中输入 / 输出三项**全部减半**，没有按模型族区分折扣。
4. 峰谷只影响 **API token 单价**；网页版/App 聊天不适用该价格表。插件定时发送的是 DSH 消息 → 最终触发的是 API 请求，所以适用。
5. 官方文档**未说明**「跨边界的请求按开始还是完成时间计价」——这条置信度低，插件按「请求在谷价时段内开始」排期并留安全余量即可（见 §5）。
6. **插件当前 `plugin/client.js` 顶部的 `OFF_PEAK = 00:30–08:30` 是过时口径**，会让「当前是否谷价」在一天大部分时间判断错误、并让「等谷价」不必要地等很久（见 §8）。

## 1. 现行峰 / 谷窗口（置信度：高）

官方定价页脚注（[中文版](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[英文版](https://api-docs.deepseek.com/quick_start/pricing/) 两版一致）：

- 北京时间（Asia/Shanghai，UTC+8）：
  - **高峰**：周一至周五 `09:00–12:00`、`14:00–18:00`（不含中国法定节假日）。
  - **空闲 / 谷价**：其余所有时段，包括**周末全天**与**中国法定节假日全天**。
- UTC 等价表达（英文页原文）：高峰为周一至周五 `01:00–04:00`、`06:00–10:00` UTC（排除中国法定节假日）；其余时段为空闲。
- 中文原文：「空闲时段价格为高峰时段价格的一半。北京时间周一至周五（不含中国法定节假日）9:00 - 12:00、14:00 - 18:00 为高峰时段；其余时段，包括周末及中国法定节假日全天均为空闲时段。」
- 边界：文档按 `9:00 - 12:00`、`14:00 - 18:00` 的半开区间表述；代码建议按 `[09:00,12:00)`、`[14:00,18:00)` 判高峰，`12:00:00` / `18:00:00` 起算谷价（排期本身还要加安全余量，见 §8）。
- 时区：官方以**北京时间**为计费基准，海外用户也按北京时间换算；**不要**按用户本地时区换算，会算错。

### 判定逻辑（可直接照抄）

```
isPeak(t) =
     weekday(t, Asia/Shanghai) ∈ Mon..Fri
  && NOT isChinaPublicHoliday(date(t))          // 节假日全天非高峰
  && ( 09:00 <= hh:mm(t) < 12:00 || 14:00 <= hh:mm(t) < 18:00 )

isOffPeak(t) = NOT isPeak(t)
```

> 注：官方没有提供「中国法定节假日日历」接口。插件若不内置国务院放假表，至少把周末判对；节假日可先按「未知 → 保守按高峰显示」或做成可配置项（见 §8）。

| | 输入·缓存未命中 | 1 | 2 |
| | 输出 | 4 | 8 |
| `deepseek-v4-pro` | 输入·缓存命中 | 0.15 | 0.30 |

## 3. 周末 / 中国法定节假日（置信度：高；调休推导为中高）

- **周末**：周六、周日全天按空闲/谷价计费（官方脚注：「包括周末」）。
- **中国法定节假日**：全天按空闲/谷价计费（官方脚注：「不含中国法定节假日」→ 节假日不进入高峰）。
- **调休补班**（周六/周日上班）：官方高峰前提是「周一至周五且非法定节假日」，因此**落在周六/周日的补班日仍按周末 → 全天谷价**。这是对官方措辞的直接推导，无逐字官方说明，置信度中高。
- **2026 年与工作日不同的点**就是上面这些：周末/节假日没有高峰段，全天谷价；官方没有「周末额外折扣」或「节假日加价」的口径。

## 4. 旧窗口 00:30–08:30 的历史与现状（历史：中；「已过时」：高）

- 2025-02-26 起，DeepSeek 曾推出夜间错峰优惠：**北京时间每日 00:30–08:30**，`deepseek-chat`（V3）降至 5 折、`deepseek-reasoner`（R1）降至 2.5 折（第三方新闻转述，官方历史公告页现已不可直接访问，故置信度中）。
- 该方案已被后续价格体系取代：**2026-08-17 起官方改为「工作日两段白天时间为高峰」的峰谷定价**；2026-11-09 的官方定价页**没有任何 00:30–08:30 的表述**。
- 因此 **00:30–08:30 不能作为插件默认谷价窗口**：它恰好落在现行谷价内（不会亏钱），但
  1. 谷价时段远不止这 8 小时（工作日约 19 小时 + 周末/节假日全天），用它当默认会让人误以为只有凌晨便宜；
  2. 「当前已在谷价」判断在一天中大部分时间会错；
  3. 「下一个谷价开始」可能白等：例如 13:00 时已过 00:30，按旧窗口要等到次日 00:30，但当天 18:00 起就是谷价。

## 5. 折扣是否「按请求开始时间」判定？（置信度：低 / 官方未证实）

- 现行官方定价页、更新日志、新闻页**均未写明**：恰好跨高峰/谷价边界的请求，是按**请求开始时间**还是**完成时间**计价，也未说明流式/长请求如何切分。
- 工程上稳妥的做法（不依赖未证实规则）：
  1. 只让**请求开始时刻**落在谷价窗口内，并留 **≥1–2 分钟安全余量**（例如排到 `12:02`、`18:02`，而不是 `12:00`、`18:00` 整点，避免时钟/调度抖动把开始时刻推到高峰一侧）。
  2. **长任务可能跨入高峰**：DSH 中一条用户消息会触发多次 API 请求（工具调用、多轮续写等），每次请求各自按自身时刻计价；定时发送只能保证首批请求在谷价，不能保证整轮都在谷价。UI 不要承诺整轮省 50%。
  3. 如要写「省一半」，限定为官方口径「谷价时段内请求单价为高峰的 50%」，不要承诺具体账单金额。
- 建议后续用真实账单/`usage` 做一次边界实验（边界前 1 分钟发长请求，对比扣费）来升级这条置信度。

## 8. 默认值建议（给 `dsh-offpeak-send` 插件）

### 8.1 推荐实现：存「高峰黑名单」，谷价取补集

由于现行谷价在工作日是**两段不连续**的时间（`12:00–14:00` 与 `18:00–次日 09:00`），再用「单个 off-peak 窗口」建模会出错；推荐改成下面这套（时区统一 `Asia/Shanghai`）：

```js
// 高峰窗口（半开区间 [start,end)）；仅周一至周五、且非法定节假日
const PEAK_WINDOWS = [
  { start: '09:00', end: '12:00' },
  { start: '14:00', end: '18:00' },
];
// 周六/周日、中国法定节假日：全天谷价（不进入 PEAK_WINDOWS）

// 插件「等谷价发送」预设的默认目标（北京时间）：
//   当前已在谷价        → 立即发送（沿用已有的 >=60s lead 即可）
//   当前在 09:00–12:00 → 12:02（= 高峰结束 12:00 + 2 分钟安全余量）
//   当前在 14:00–18:00 → 18:02（= 高峰结束 18:00 + 2 分钟安全余量）
const BOUNDARY_MARGIN_MIN = 2;   // 建议 ≥1，默认 2
```

- 「下一个谷价开始」= 若在高峰期，取**当前高峰段的结束时刻 + 余量**（`12:02` / `18:02`）；否则就是「现在」。
- 若还要保留「谷价窗口结束」倒计时：下一个高峰开始为工作日 `09:00`（周末/节假日后顺延到下一个工作日），同样加余量。
- UI 展示可用「谷价 = 工作日 12:00–14:00、18:00–次日 09:00，周末及中国法定节假日全天」。

### 8.2 若产品坚持只存「一个窗口对」（不推荐，仅兜底）

- 用 **`18:00` – 次日 `09:00`** 作为展示/默认的「主谷价窗口」（跨午夜，工作日晚间到次日清晨，连续 15 小时，是工作日最长的谷价段）；
- 同时必须在文案里补上「工作日 `12:00–14:00`、周末/节假日全天也是谷价」，否则判断与文案都会不完整；
- 旧的 **`00:30–08:30` 不要再作为默认值或窗口文案出现**（它只是谷价的一个子集）；若确实需要一个「任何一天都必定在谷价内」的固定发送时间兜底，用 `00:30` 这个时间点可以，但不能把它叫作「谷价窗口」。

### 8.3 UI 一行提示（可放输入框下方 / 弹层说明）

- 中文：`谷价＝高峰价 5 折，仅 API 计费：工作日 12:00–14:00、18:00–次日 09:00，周末及中国法定节假日全天（北京时间）；高峰为工作日 09:00–12:00、14:00–18:00，价格/时段可能调整，以官方定价页为准。`
- English: `Off-peak = 50% of peak, API billing only: weekdays 12:00–14:00 and 18:00–09:00, plus all weekend and Chinese public holidays (Beijing time); peak = weekdays 09:00–12:00 and 14:00–18:00. Prices/windows may change — see the official pricing page.`

可选补充一行（长任务提醒，中文 + English）：
- 中文：`定时发送只保证开始时刻在谷价内；多轮/长任务的后续请求按各自时刻计价。`
- English: `Scheduling guarantees only that the request starts off-peak; later requests in a long or multi-turn run are billed at their own times.`

### 8.4 与当前插件实现的差异提醒（供 Lead 决策，本文件不改代码）

- `plugin/client.js` 顶部当前为 `OFF_PEAK = { startHour: 0, startMinute: 30, endHour: 8, endMinute: 30 }`（北京时间 00:30–08:30），并配套 `ofsendNextOffPeakStart/End`、`ofsendInOffPeak`、`offpeak` 预设。按 2026-11-09 官方口径，这套默认值应替换为 §8.1 的「高峰黑名单 + 补集」逻辑；`scripts/test-client.mjs` 中锚定 00:30–08:30 的用例（如 “off-peak window is Beijing 00:30-08:30”）也需要同步改为新窗口断言。
- 最小可上线改动（如果时间紧）：保留单窗口结构，把窗口换成 `18:00–次日 09:00`，并把文案补全（§8.2），同时把「下一个谷价开始」改为「高峰期结束 + 余量」；但这样在周末/午间仍会误判，建议还是做 §8.1。
